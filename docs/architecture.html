01 — Why this exists

Overview & goals

Every test needs a different mix. One simulation might lean toward language literacy, another toward mathematics or economics. This platform lets an admin encode that mix once, per Test, and have every invited candidate receive a freshly assembled test that honors it — without hand-picking questions each time.

🎯 Personalized by role

A Test defines topic percentages, an optional easy/medium/hard split, question count, time limit and passing score. The generator samples the bank to match.

⏱ Timed, single-session

The timer is anchored server-side at start time. The candidate's browser only renders a countdown to a deadline the server already computed and enforces.

🔗 Zero-friction access

Candidates need no account — a single unguessable link (a 24-character token) is their entire authentication.

04 — Storage

Six flat collections live inside data/db.json. There are no joins — related records carry each other's ids, and results denormalize the candidate/test names at submission time so history survives later edits or deletions.

Field notes

Test

topicWeights: [{category, percent}] must total 100. levelWeights is the same shape for easy/medium/hard, or null to ignore difficulty entirely when sampling.

Exam

questionIds is generated once — at invite time, not at start time — so the timer's own countdown is the only thing decided when the candidate clicks Start.

Result

Stores the full per-question breakdown (candidate's answer vs. the key, explanation) so the admin's review page needs no re-join against the live question bank.

Question

type is PG (single answer, key in correctIndex), PGK (several answers, correctIndexes) or BS (Benar/Salah per statements, key in correctAnswers). Questions about the same reading text share a passageId. The key and explanation are stripped out server-side before a question reaches the candidate's HTML — see Security.

05 — Ingestion

Question bank ingestion

The five Bank_Soal_TKA_SMA_*.md files in the project root are the source of truth for the bank. src/seed/parseBank.js reads each one and src/seed/seed.js writes the normalized result into the questions collection — safe to re-run any time the source files change. The older parseMarkdown.js is no longer used by the seed.

One format, three question types

Every file is parsed line-by-line with the same rules. A reading text (## Teks N — Title) is attached to the questions that follow it, and answers come from the Rekap Kunci Jawaban tables, with reasoning taken from the Kunci & Pembahasan blocks.

PG

Single answer, options A–E.

**1.** **[PG][Tekstual]** ...
- A. ...
- B. ...

PGK

Choose several; the key is a set such as A, C.

**3.** **[PGK][Inferensi]** ...
- A. ...

BS

A Benar/Salah table; the key is one verdict per statement, such as B–S–B.

**5.** **[BS][Evaluasi]** ...
| Pernyataan | Benar | Salah |

Where difficulty comes from

Each question carries a cognitive-level tag, which is mapped to easy / medium / hard: Tekstual and Pemahaman → easy; Inferensi and Penerapan → medium; Evaluasi, Refleksi and Penalaran → hard.

Design decision, not a measured fact The mapping is a starting point, not a certified rating. The admin's Question Bank screen lets any question's level be corrected by hand.

A server-side deadline check runs on every GET too — if a candidate abandons the tab and returns after time is up, the exam is auto-finalized with whatever was never submitted graded as unanswered, instead of hanging open indefinitely.

07 — Core logic

Weighted selection algorithm

src/services/testGenerator.js turns a Test's percentages into an exact set of question ids. The hard part is that topic and difficulty are two independent constraints being satisfied from the same finite pool — it uses largest-remainder apportionment twice, then backfills any shortfall.

  1. Apportion by topic. totalQuestions is split across categories in proportion to their percentages, rounded so the parts always sum to the whole (largest-remainder method, not naive rounding).
  2. Apportion by level, within each topic. If the Test enforces a difficulty mix, each category's share is split again across easy/medium/hard the same way.
  3. Sample without replacement from the bank for each (category, level) cell, shuffled.
  4. Backfill shortfalls — first from other levels in the same category (protects the topic weight), then from the wider bank (protects the total count), collecting a human-readable warning for every substitution made.
  5. Keep reading texts together. The final order shuffles passage groups, not single questions, so questions about one text stay adjacent and the text is shown once above them.
Why largest-remainder, not Math.round Rounding four category percentages independently can land on 41 questions or 39 instead of exactly 40. Largest-remainder apportionment (the method used to allocate parliamentary seats) guarantees the parts always sum to the requested total.

Worked example

A test set to 10 questions, topics Bahasa Indonesia 50% / Bahasa Inggris 30% / Matematika 20%, difficulty easy 40% / medium 40% / hard 20% — produces exactly:

09 — Trust boundaries

Security & integrity

✅ Answers never reach the browser early

The quiz route maps each question to {id, category, type, text, options, statements, passage…} before rendering — the answer key and explanation simply aren't in the payload, not just hidden by CSS.

✅ Server owns the clock

deadlineAt is computed once, server-side, at start. The client timer only displays a countdown to it; every request re-checks the real deadline before accepting an answer.

✅ Passwords are hashed

bcryptjs hashes the admin password; the default seeded credential is printed to the console once and documented for the operator to change.

⚠️ Token-in-URL is the whole access model

Anyone with the link can take the test — there's no second factor. Acceptable for a low-stakes take-home exercise; add email verification before using this for anything higher-stakes.
